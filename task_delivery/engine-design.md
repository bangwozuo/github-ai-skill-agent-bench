# GitHub 爆款 AI Skill / Agent 评测工作流引擎设计

## 1. 目标

把“GitHub 上看起来很火的 AI Skill / Agent”转成一条可复核决策链：

`发现值得测的项目 → 安全地装起来 → 用真实任务跑一次 → 看真实结果 → 判断是否采用 → 形成可发布但不夸大的内容候选`

最终同时交付两件东西：

1. 可复用资产：检索式、快照、候选筛选规则、冻结任务、质量门、证据校验器和报告生成器；
2. 本题交付：每个项目的实际安装/运行记录、结果、结论与建议。

## 2. “爆款”拆成四个独立问题

| 问题 | 需要什么证据 | 输出 |
|---|---|---|
| 市场是否关注 | 时点 Star/Fork、跨期增量、近期维护、真实需求来源 | 值得复现候选 |
| 能否安全复现 | 官方仓库、许可证、固定提交、隔离环境、完整安装日志 | 可复现/阻塞/失败 |
| 是否适合真实任务 | 同一冻结输入、实际结果、人工接管、可继续使用的交付 | 采用/限定试用/不适合本题 |
| 是否适合做内容 | 普通用户损失或愿望、可见反差、5—10秒决定性证明、内容库去重 | 高潜内容候选 |

没有任何一个单项能代替另外三个。Star 多不能证明结果好；本地成功也不能证明市场会传播。

## 3. 候选发现引擎

### 3.1 四路检索

- Topic：`agent-skills`、`ai-agent`；
- 名称/简介关键词：`agent skill`、`AI agent`；README 只用于进入候选后的能力审阅，不用于宽泛拉新；
- 老牌高热：按 Star 排序，识别已形成广泛关注的项目；
- 新近加速：定期保存相同查询快照，用 `ΔStar / 观察天数` 发现增量。

检索式全部版本化保存在 `workflow_asset/discovery-config.json`。查询门槛只控制研究成本，不是质量或传播评分。

### 3.2 去重与身份

同一个 `owner/repo` 在多条查询里只保留一个候选，并记录命中的查询。Fork、镜像、合集中的子项目和原项目不混为一项；正式评测前再通过官方仓库接口冻结 40 位提交 SHA。

### 3.3 三层队列

- `reproduction_candidate`：热度或增量信号存在，近期仍维护，许可证已识别，非归档/禁用/Fork；
- `market_watch`：有市场信号，但许可证、维护或来源存在硬阻塞，只观察不安装；
- `background`：当前信号不足，不占用复现资源。

## 4. 真实适用评测

### 4.0 先过账号、爆款初筛与可行性三门

候选不能从“仓库热度高”直接跳到安装。先用 `GITHUB-AI-CANDIDATE-EDITORIAL-REVIEW-2.0` 锁定三组不可互相抵消的事实：

- 账号适配：USE 必须是具名对象、单一任务、可见结果和人工判断；FLOW 必须是重复触发、多阶段交接、人工停点、任务交付与可复用资产。每条还要写明为什么不能原样换到另一个账号。
- 爆款逻辑初筛：明确主要吸引机制、标题承诺、封面回报、前五秒首证、可带走资产、保存/转发理由和真实性边界。这里只叫初筛，不叫正式爆款评审。
- 可行性：选择一个最小运行路线，标明低/中/高复杂度、隔离环境、无密钥、代表输入、验收、成本上限、停止条件和一到三次最大运行次数。

运行 `github-ai-bench validate-editorial --input <review-or-batch.json> --output <receipt.json>`。校验器会拒绝缺受众、跨账号理由、账号原生链、五秒证明、停止条件的候选，也会拒绝没有哈希评审文件却手填“正式爆款评审通过”。其 PASS 仅允许进入隔离复现，不授权完整文本准入、生产或发布。

### 4.1 每个候选先写一张任务卡

- 谁在什么真实时刻使用；
- 输入是什么；
- 想得到哪个可直接查看或继续编辑的交付；
- Skill / Agent 真正封装了哪项规则、动作或资源组织；
- 哪些动作必须停在人手里；
- 怎样算成功，怎样算“不适合本题”。

没有真实任务，不进入安装。不能为了让项目显得有用而临时发明场景。

### 4.2 统一测试与项目原生测试并存

- 统一基准题：用于多个项目做公平比较，输入和验收完全一致；
- 项目原生任务：用于验证它最核心、最不可替代的能力，不拿错误任务误伤项目。

如果公开主题是“谁更适合这项任务”，用统一题；如果主题是“这个项目能带来什么能力”，先跑原生题，再把对照当证明模块。

### 4.3 隔离安装

不受信任仓库只能进入一次性容器、Windows Sandbox 或虚拟机。构建期联网只为官方依赖，运行期默认断网；不提供个人目录、浏览器资料、SSH、Token、Cookie、真实客户数据、宿主 Docker Socket 或管理员权限。

若项目必须使用真实密钥、云账号或外发数据，本轮状态记为 `blocked`，由人决定是否扩大权限。不能为了完成评测偷偷降低安全边界。

### 4.4 同一运行证据链

`官方仓库 → 许可证 → 固定提交 → 环境 → 冻结输入 → 安装日志 → 运行日志 → 结果 → 可选可视过程 → 人工判断`

每项都写入 SHA256。不能把 A 版本的页面、B 版本的日志和 C 版本的截图拼成一次成功。

## 5. 结果展示

评测报告第一屏只给四件事：

1. 项目身份和固定提交；
2. 本次任务；
3. 实际结果或明确失败位置；
4. 人工采用建议和窄结论。

完整日志放在下钻层，不把审计字段堆到面向普通观众的画面。若要声称 `native_run`，必须有真实连续操作记录和可视 QA；只有结果文件时最多声称 `actual_result`。

## 6. 结论规则

- `采用`：当前真实任务成功，交付可用，人工接管清楚，成本与风险可接受；
- `限定试用`：结果可用，但依赖、成本、稳定性或人工核对仍需观察；
- `不适合本题`：项目能运行，但对这项任务的收益不足或结果不可采用；
- `本次复现失败`：保留失败阶段和日志，不外推为项目整体缺陷；
- `当前环境受阻`：系统、账号、网络、密钥或权限不匹配，结论停在适用边界；
- `HOLD`：身份、许可证、输入、日志、结果或主张任一证据不完整。

不做一个可相互抵消的总分。只有同任务、同输入、同环境级别、同验收、同时间窗口的项目，才进入横向对比。

## 7. 内容挖掘规则

本题以“是否采用”作为主问题，采用 AS-C 独立评测候选：

`具体任务的收益差异 → 共同条件与验收 → 起作用的动作 → 收益与代价 → 适用结论`

若某项目的真正吸引力是“以前难获得的专业能力现在有入口”，用 AS-A，评测只做信任证明；若是“替我选好的能力包”，用 AS-B，比较只解释为什么这样选。

标题、封面和前五秒先给普通人的任务、损失、结果或反差；工具名和工作流图属于证明层。每个候选至少要回答：

- 观众原来只能做到哪一步，目标结果是什么；
- 这个 Skill/Agent 删除后会失去哪项实质能力；
- 最强结果在 5—10 秒内能否读懂；
- 看完能带走测试题、规则、清单还是可运行资产；
- 与内容库已有“高 Star Skill”“GitHub 筛选”“平台横评”作品有什么实质差异。

## 8. 建议的运行节奏

- 每周保存 1 次同口径快照；
- 每周只把 3—5 个项目推进到人工任务价值审阅；
- 每次只复现 1—2 个项目，避免并行安装扩大风险；
- 每个项目默认 1 个代表性任务和 1 次正式运行；
- 只有公开承诺可复跑，才用变化输入做第二次；
- 发布后记录真实平台、日期、分母、主要改动、反馈、混杂因素与反例，再调整选题规则。

## 9. 现有工作流与 GitHub 双出口

一次通过的评测只派生两种输出，不修改现有 Skill 或内容库：

- `export-handoff` 生成只读 FLOW 交接回执，现有完整文本、质量审核、用户批准、准入、录制和交付门禁继续拥有全部状态；
- `package-work` 生成一个作品一个仓库的公版包，只含原创代码、脱敏输入/输出、评测回执、结论边界、许可证与来源声明。

公版包不复制第三方源码、已安装 Skill、内部生产回执或私有材料。缺少精确 GitHub 目标时只能是 `draft_ready`；目标和当次授权齐全才是 `ready_for_publish`。详情见 `docs/existing-workflow-integration.md`。
